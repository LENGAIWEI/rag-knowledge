# RAG 检索三层详解

这篇讲的是 `rag-knowledge` v2 检索链路的**为什么**——每一层解决了什么失败模式、
公式怎么来的、参数怎么调、以及面试时最可能被追问的点。

v1 的链路是一层：`向量化 → 余弦相似度 → 阈值过滤 → topK → 拼 Prompt`。
它能跑，但**失败模式很集中**，下面每一层都对应一类具体的失败。

---

## 0. 先看失败模式，再看方案

| 用户输入 | v1 的表现 | 根因 | v2 靠哪一层解决 |
| --- | --- | --- | --- |
| "它需要提前几天申请？"（承接上文"年假"） | 检索不到任何相关段落 | 查询里有指代，向量和关键词都无从匹配 | ① Query 改写（指代消解） |
| "怎么请假" / 文档写"休假申请流程" | 时好时坏 | 查询词和文档词完全不重叠（词汇鸿沟） | ① 同义改写 + ② 向量路 |
| "ISO-9001 的审核周期" | 可能召回到讲 ISO-9002 的段落 | 向量空间里 `ISO-9001` 和 `ISO-9002` 几乎重合 | ② BM25 路 + ③ 精排的短语特征 |
| "年假？"（两个字） | 召回一堆泛泛而谈的段落 | 查询太短，向量落在语义空间中心 | ① HyDE |
| 答案确实被召回了，但排在候选池第 12 位 | topK=3 时被截掉，模型答不出来 | 召回只能保证"在里面"，不能保证"在前面" | ③ 精排 Rerank |
| 知识库里根本没有答案 | 硬凑一段给模型，模型跟着编 | 只有相对阈值，没有绝对门槛 | 阈值设计（见 §3.4） |

**核心认知：召回决定上限，精排决定下限，改写决定上限有多高。** 三者不是替代关系，
每加一层都是在堵一类漏。

## 1. 第 1 层：Query 改写 / HyDE

### 1.1 指代消解

多轮对话里，"它""这个""那上面说的"占相当大的比例。这类查询直接拿去检索必然失败，
因为**指代信息不在查询里**。

做法：把最近几轮问答一起交给 LLM，让它输出一个**不依赖上下文就能独立检索**的问题。

```
历史：Q: 公司的年假是怎么规定的？  A: 工龄满一年享五天年假。
本轮：它需要提前几天申请？
改写：年假需要提前几天申请？         ← 拿这句去检索
```

注意：**最终给大模型作答时用的仍然是用户的原问题**（"它需要提前几天申请？"），
改写结果只用于检索。改写是"给检索器的翻译"，不是"给用户的答案"。

### 1.2 多查询扩展（Multi-Query）

词汇鸿沟是 RAG 最顽固的问题之一：用户说"怎么请假"，文档写"休假申请流程"，
两边**语义相同但一个词都不重合**。

向量检索能缓解，但缓解得有限——尤其是短查询。更稳的做法是一次生成几个同义改写：

```
原问题：怎么请假
变体1：休假申请流程是什么
变体2：员工请假的办理步骤
```

每条查询**各自召回一批**，再融合。逻辑是**共识投票**：一个段落被越多条改写同时召回，
它越可能是真的相关。这比"把所有改写的向量平均一下再去检索"要好——
平均会抹平差异，而多路召回保留了每一路的独立判断。

### 1.3 HyDE（Hypothetical Document Embeddings）

原理来自 2022 年的论文 *Precise Zero-Shot Dense Retrieval without Relevance Labels*：

> 与其用**问题**的向量去匹配**文档**的向量（两者分布差异很大），
> 不如先让模型**编一段假答案**，用假答案的向量去匹配真文档的向量——
> 假答案和真文档的**分布是同一类**（都是陈述句、都用领域术语）。

```
问题：年假？
假答案（LLM 生成，可能事实全错）：
  根据公司员工手册规定，员工年假天数与工龄挂钩：工龄满一年可享受五天年假，
  满三年可享受十天年假。年假需提前三个工作日通过 OA 系统提交申请……
                ↓ 用它的向量去检索
真实文档里的段落会被排到更前面，因为用词和句式高度相似
```

**三个必须讲清楚的陷阱：**

1. **假答案绝不能进 Prompt。** 它只是探针。如果把它连同真片段一起给大模型，
   模型会把编造的"提前三个工作日"当成事实——这是把幻觉从生成阶段提前到了检索阶段。
   本工程的实现里，HyDE 文本只用于算向量，`buildPrompt()` 里根本拿不到它。
2. **它不保证事实正确，也不要求事实正确。** 它利用的是"分布对齐"，不是"知识正确"。
3. **成本是实打实的一次 LLM 调用。** 所以默认关闭（`kb.hyde.enabled=false`），
   在页面上做成显式开关。**面试时主动说出这个取舍，比说"我用了 HyDE" 更加分。**

### 1.4 一次调用同时产出三种结果

改写处在关键路径上，每多一次 LLM 往返就多一两秒首字延迟。
所以这里**合并成一次调用**，用一个结构化 prompt 同时拿到：

```json
{
  "standalone": "年假需要提前几天申请？",
  "variants": ["休假申请流程是什么", "员工请假的办理步骤"],
  "keywords": ["年假", "请假", "申请", "提前"]
}
```

解析用 Jackson，提示词里明确要求"只输出 JSON、不要 markdown 代码块"。
即便如此，LLM 偶尔还是会包一层 ```json，所以代码里做了 `extractJson()`
剥壳（截取第一个 `{` 到最后一个 `}`）——**这是在实测中踩出来的，不是防御性编程的洁癖**。

## 2. 第 2 层：混合检索（向量 + BM25 → RRF）

### 2.1 为什么必须有 BM25

向量检索的弱点是**精确匹配**。它把文本压成一个稠密向量，
`ISO-9001` 和 `ISO-9002` 在高维空间里几乎是同一个点——因为它们语义确实几乎相同。
但用户查型号、条款号、错误码、人名时，**差一个字符就是完全不同的东西**。

BM25 是关键词检索的事实标准，两者正好互补：

| | 向量检索（Bi-Encoder） | BM25 |
| --- | --- | --- |
| 同义转述（"怎么请假" vs "休假申请流程"） | ✅ 强 | ❌ 完全无能为力 |
| 精确词 / 编号 / 型号 | ❌ 弱 | ✅ 极准 |
| 长文档中的关键词 | 一般 | ✅ 长度归一化后表现好 |
| 需要模型 / 训练 | 需要 | 不需要，统计即可 |
| 可解释性 | 弱 | 强（哪个词贡献了多少分，一目了然） |

### 2.2 中文分词：为什么用 bigram

BM25 的效果几乎完全由分词决定。中文没有空格，三条路：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 接分词器（jieba / HanLP） | 精度最高 | 引入依赖；未登录词（新词、人名、产品名）会切错，一旦切错就彻底漏召回 |
| 单字切分 | 零依赖 | 精度极差，"请假"变成"请"+"假"，"请"会和无数无关文档撞车 |
| **二元组 bigram**（本工程） | 零依赖；召回率接近分词器；对未登录词天然稳健 | 索引略大；会有少量无意义组合 |

实现规则：

```
"请假需要提前几天？" → [请假, 假需, 需要, 要提, 提前, 前天, 几天]
"ＲＡＧ 知识库 v2"   → [rag, 知识, 识库, v2]
```

顺带处理了三个实际会遇到的坑：

- **全角转半角**：用户输入法经常打出全角字母数字（`ＲＡＧ`），不归一化就检索不到；
- **大小写归一**：`SpringBoot` / `springboot` / `SPRINGBOOT` 应该是同一个词；
- **停用词**：英文停用词直接过滤；中文停用词只对单字生效（否则"需要"会被拆开误杀）。

> 这里有一个真实的踩坑记录：全角转半角之后**还必须再转一次小写**。
> 最初把两者写成 `if / else if`，导致 `Ｒ` 转成半角大写 `R` 之后就不再进小写分支，
> 而后续的字符判定只认 `a-z`，于是整个 `ＲＡＧ` 被当成噪声字符丢掉。
> 这是靠单元测试跑出来的，不是靠读代码看出来的。

### 2.3 BM25 公式

对查询里的每个词 `t` 累加：

```
IDF(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))

score += IDF(t) · ─────────────────────────────
                    tf · (k1 + 1)
                  ────────────────────────────────
                  tf + k1 · (1 - b + b · dl/avgdl)
```

| 符号 | 含义 | 直觉 |
| --- | --- | --- |
| `tf` | 词 t 在该块中出现的次数 | 出现越多越相关 |
| `df(t)` | 包含 t 的块数 | 越稀有越有区分度（IDF） |
| `dl / avgdl` | 块长度 / 平均块长度 | 长度归一化 |
| `k1`（默认 1.2） | 词频饱和参数 | 防止"同一个词刷 20 遍"就冲到第一 |
| `b`（默认 0.75） | 长度归一化强度 | `b=0` 不归一化，`b=1` 完全归一化 |

**两个面试常问的点：**

- **为什么要饱和（`k1`）？** 因为词频的边际收益是递减的。一个词出现 3 次和出现 30 次，
  相关性的差别远远小于 0 次和 3 次的差别。线性累加会让刻意堆砌关键词的文档霸榜。
- **为什么要长度归一化（`b`）？** 长文档天然包含更多词，不归一化的话"长"就等于"相关"。

倒排表用扁平 `int[]` 存储 `[ordinal, tf, ordinal, tf, ...]`，比 `List<Posting>`
省掉大量小对象；IDF 在建索引时预计算，查询时只做数组遍历。

### 2.4 RRF 融合：为什么不用加权求和

**这是最容易被追问的一点。**

朴素做法是把两路分数加权相加：

```java
score = 0.5 * cosine + 0.5 * bm25;   // ← 错的
```

问题在于**两路的分数不可比**：

- 余弦相似度被限制在 `[0, 1]`；
- BM25 是无上界的正数——本文档集里可能是 `37.8`，换一批语料可能变成 `3.2`。

量纲差了两个数量级，加权求和的结果实际上是 **BM25 单方面主导**，
而且每换一次语料就要重新调权重。

RRF（Reciprocal Rank Fusion，Cormack et al., SIGIR 2009）**只用排名，不用分数**：

```
RRF(d) = Σ_routes  weight_route / (k + rank_route(d))        k 默认 60，rank 从 1 开始
```

排名是无量纲的，所以天然免疫量纲差异。`k` 控制"民主程度"：

- `k` 越大，各名次之间差距越小，越接近"投票"；
- `k` 越小，越接近"赢者通吃"（第 1 名权重 `1/1`，第 2 名 `1/2`）。

本工程还把**多查询扩展**接进同一个融合公式：

```
RRF(d) = Σ_queries Σ_routes  w_query · w_route / (k + rank(d))
```

权重体现"这一路有多可信"：

| 来源 | 默认权重 | 理由 |
| --- | --- | --- |
| 原问题 | `1.0` | 用户亲口说的，最可信 |
| 改写后独立问题 | `0.9` | 消解了指代，但经过模型转述 |
| 同义变体 | `0.6` | 探索性召回，可能跑偏 |
| 关键词（只走 BM25） | `0.6` | 抽取出的"词"拿去算向量反而污染向量路 |
| HyDE 假设答案 | `0.8` | 分布对齐有效，但内容是编的 |

RRF 分本身很小（量级 `0.01~0.05`），且**没有绝对量纲**——所以它只用来排序，
不做阈值判断。绝对门槛交给精排分（见 §3.4）。

## 3. 第 3 层：精排 Rerank

### 3.1 Bi-Encoder vs Cross-Encoder（必问）

这是 RAG 精排部分的**头号考点**。

```
Bi-Encoder（召回用）—— 查询和文档分别编码，从不交互
    查询 ──▶ [Encoder] ──▶ 向量 q  ┐
                                    ├─▶ 余弦相似度
    文档 ──▶ [Encoder] ──▶ 向量 d  ┘   （文档向量可以离线算好）

Cross-Encoder（精排用）—— 查询和文档拼在一起，让注意力自由交互
    [CLS] 查询 [SEP] 文档 [SEP] ──▶ [Encoder] ──▶ 相关性分数
```

| | Bi-Encoder | Cross-Encoder |
| --- | --- | --- |
| 查询与文档的交互 | **无** | 注意力层内部充分交互 |
| 文档向量能否预计算 | ✅ 能，可建 ANN 索引 | ❌ 不能 |
| 复杂度 | 查询向量 + ANN 检索 | 每个 (查询, 文档) 对跑一次前向 |
| 精度 | 一般 | 显著更高 |
| 用途 | 从百万文档里召回 top100 | 把这 100 条精排成 top5 |

**结论就是那句经典的架构：粗排召回 + 精排重排。**
用廉价的召回把候选压到精排能承受的规模（本工程默认 20 条），再用昂贵的精排定序。
`bge-reranker-v2-m3` 在 CPU 上处理 20 条 300 字候选约 0.6~2 秒——
如果拿它去扫全库 118 个块还能忍，扫 10 万个块就完全不可行了。

### 3.2 本地精排：没有模型时怎么模拟交叉编码器

本工程刻意不引入 DJL / ONNX Runtime，所以默认路径是一个**纯 Java 的手工特征精排器**。
它的思路是：把 cross-encoder 靠注意力隐式学到的"交互信号"，手工拆出来加权。

| 特征 | 默认权重 | 模拟的模型能力 |
| --- | --- | --- |
| 向量余弦（绝对分） | 0.30 | 整体语义相似度（双塔已经给出的信息） |
| IDF 加权词项覆盖率 | 0.25 | "查询里的关键信息，文档答到了几个" |
| 邻近密度 | 0.20 | "这些词是凑在一起，还是散落在全篇" |
| 最长公共子串 | 0.15 | 精确短语命中（条款号、型号、原文摘抄） |
| BM25（饱和归一） | 0.10 | 关键词强度 |

**三个值得展开的设计：**

**① IDF 加权覆盖率。** 分母是查询里所有词的 IDF 之和，分子是文档命中的那些词的
IDF 之和。用 IDF 加权而不是简单计数——"的""是"命中了没有意义，
而"年假""ISO-9001"命中一次就说明问题。

**② 邻近密度。** 把文档里命中查询词的位置抽出来，用滑动窗口找
"包含最多个不同查询词的最小区间"：

```
proximity = (窗口内不同查询词数 / 查询词总数) × (窗口内不同查询词数 / 窗口长度)
             └────── 答到了多少 ──────┘   └────── 有多紧凑 ──────┘
```

两项都必要：只算紧凑度的话，只命中一个词但恰好落在同一位置也会得满分。

**③ 所有特征输出绝对分，不做候选集内归一化。** 这一点很关键，
下面单独说。

### 3.3 精排层最容易被忽略的坑：分数归一化的位置

一个很常见的实现是：算完精排分后，对候选集做 min-max 归一化再展示/过滤。

```java
// 看起来没问题，实际是灾难
normalize(candidates);                       // 最高分变成 1.0，最低分变成 0.0
filter(c -> c.score >= minScore);
```

**后果是永远无法拒答。** 因为排名第一的候选**永远**会被归一化成 `1.0`，
无论它实际上有多不相关。知识库里根本没有答案时，系统依然会把最不烂的那一段
塞给大模型，然后模型照着编。

本工程的做法：

- **本地精排的每个特征都输出绝对分**（余弦本来就是绝对的；BM25 无上界，
  用 `x/(x+8)` 饱和到 `[0,1]` 再乘 0.6 折算），加权和自然也是绝对分；
- **远程精排**：`bge-reranker` 多数推理服务输出的是未过 sigmoid 的 logit，
  代码里判断"若分数不全在 `[0,1]` 区间就做 sigmoid"，
  而不是简单地 min-max——后者会丢掉绝对信息；
- **拒答判定**基于候选池与绝对门槛，而不是相对排名。

### 3.4 两个阈值，职责不同

参数变多容易让人困惑，所以这里明确区分：

| 参数 | 默认 | 作用 | 失效时 |
| --- | --- | --- | --- |
| `kb.recall.min-vector-score` | `0.25` | **向量路召回门槛**：余弦低于它不进候选池 | 调低 → 召回更多但更杂 |
| `kb.rerank.min-score` | `0.15` | **精排后最终门槛**：绝对分低于它的候选直接丢弃 | 调高 → 更容易拒答 |

BM25 路**不设绝对阈值**，只取 topN。这是关键词检索的性质决定的：
只要词命中就可能是相关的（尤其是稀有词），而 BM25 分数的绝对值高度依赖语料，
设一个固定的绝对门槛反而不可移植。

**"拒答"是 RAG 的一等公民。** 一个永远不拒答的 RAG 系统，在知识库没有答案时
必然会编——这比"我不知道"糟糕得多。

### 3.5 可插拔 + 自动降级

精排被设计成一个 SPI：

```
Reranker（接口）
 ├── LexicalReranker   纯 Java，零依赖，默认路径
 ├── HttpReranker      bge-reranker / Jina / Cohere / TEI 兼容的 /rerank 协议
 └── RerankerRouter    模式选择 + 失败降级
```

```properties
kb.rerank.mode = off | local | http | auto
```

| 模式 | 行为 |
| --- | --- |
| `off` | 不精排，保持 RRF 融合序（消融对比用） |
| `local` | 纯 Java 精排 |
| `http` | 调 bge-reranker 服务；**失败或超时自动降级为 local 并标记 `degraded`** |
| `auto`（默认） | 配了 `api-url` 走 http，否则走 local |

**为什么 http 失败不直接报错？** 精排是"锦上添花"的一层，它挂掉时融合分排序依然可用。
把它做成硬依赖，等于让一个可选组件拥有拖垮整个服务的能力。降级 + **明确标记**
（`degraded=true` 会显示在页面顶部）才是正确的取舍：用户看到的是
"这次没用上精排模型"，而不是一个 500。

> **面试可以主动说的点**：把远程精排的 URL 填成一个不存在的端口，
> 页面会显示黄色提示条"远程精排服务不可用，已降级为本地精排"，问答照常返回。
> 这条降级路径是实测过的。

## 4. 切段：为什么按标题切

朴素做法是"整篇按字数硬切"。它有三个问题：

1. **跨块语义断裂**——一个条例被切成两半后，任何一半都不足以回答问题；
2. **没有出处**——命中片段只知道来自哪个文件，不知道来自哪一节，
   用户无法核对，也无法在大模型答错时定位；
3. **标题被当正文**——标题行本身是有信息量的，硬切会把它和正文割开。

v2 的做法：

```
# 员工手册              ← 层级 1
## 请假制度             ← 层级 2
### 年假                ← 层级 3
工龄满一年享五天年假。   ← 正文

→ Chunk{ text: "### 年假\n工龄满一年享五天年假。",
         section: "员工手册 > 请假制度 > 年假" }
```

要点：

- 维护一个**标题栈**，靠层级比较实现"遇到同级或更高级标题就出栈"，
  拼出 `一级 > 二级 > 三级` 的路径；
- 标题感知只在**同一章节内**继续按 `chunkSize` 硬切 + 相邻 `overlap` 重叠；
- **章节路径参与 BM25 检索**：`indexableText()` 返回 `section + "\n" + text`，
  所以查"请假制度"能召回该节下的全部段落；
- **只有标题、没有正文的小节不产生空块**（`# 员工手册` 紧跟着 `## 请假制度` 这种）；
- 非 Markdown 文档（纯 txt、粘贴的会议纪要）自动退化为"全文章节为空"的老切法，行为不变；
- 中文式标题（`第一章` / `第三节`）也认，但加了**行长度限制**，
  避免把"第三节讲的是……"这种正文误判成标题。

## 5. 性能实测

在**本机 CPU、118 个知识块、embedding-3 向量**下的实测数据（页面「检索轨迹」会实时显示）：

| 阶段 | 耗时 | 说明 |
| --- | --- | --- |
| Query 改写 | 1351 ms | 一次 LLM 调用，产出独立问题 + 2 个变体 + 6 个关键词 |
| 向量化 | 1209 ms | **所有检索式合并成一次** Embedding 请求 |
| 双路召回 + RRF | 57 ms | 纯内存计算：118 条余弦 + BM25 倒排遍历 |
| 精排（local） | 11 ms | 20 条候选 × 5 个特征 |
| 生成答案 | 711 ms | 大模型调用 |
| **合计** | **2877 ms** | |

**几个值得说的点：**

- **精排几乎不花时间**（11ms）。它是三层里最划算的一层——如果只能加一层，加精排。
- **改写占了接近一半的时间**（1351ms），而且它和"向量化 + 召回 + 精排"是**串行**的。
  这是当前架构最明显的优化点：可以把改写做成**流式**（边改边召回），
  或者对简单查询（无指代、足够长）直接跳过改写。
- **向量化只发一次请求**，无论有几个查询变体。Embedding 接口支持 `input` 数组批量，
  4 个检索式合并成 1 次 HTTP 往返，比逐个调用省掉 3 次网络开销。
- **召回 + 融合只有 57ms**（`O(N·d)` 全量扫描 + 倒排遍历）。这个规模下引入向量数据库
  是过度设计；一旦块数上万，把 `HybridRetriever.vectorRecall()` 换成
  HNSW/IVF 索引即可，**调用方接口不变**。

## 6. 常见追问速查

**Q: 为什么不做成"两路分数加权求和"，非要用 RRF？**
见 §2.4。核心是量纲不可比：余弦在 `[0,1]`，BM25 无上界，加权求和会让 BM25 实质主导，
且换语料就要重新调权重。RRF 只用排名，天然免疫。

**Q: RRF 的 `k=60` 怎么来的？**
经验值，来自原论文。`k` 越大越"民主"（各名次差距小），越小越"赢者通吃"。
它是超参但不是敏感超参，60 是不错的默认。

**Q: 精排为什么不用向量模型直接算相似度？**
召回用的就是向量相似度。精排的意义在于**引入查询和文档的交互**——
向量相似度是两个独立编码结果的比较，看不到"这个数字对不对得上""这个条件是否被满足"。

**Q: HyDE 生成的假答案会不会污染回答？**
不会——本工程里 HyDE 文本只用于算向量，`buildPrompt()` 拿不到它。
这正是 HyDE 最容易被实现错的地方。

**Q: 知识库里没有答案时怎么办？**
靠 `kb.rerank.min-score` 这个**绝对**门槛拒答。注意不能用候选集内归一化的分数做门槛，
否则第一名永远是 1.0，等于永远不拒答（见 §3.3）。

**Q: 为什么中文用 bigram 而不是接 jieba？**
零依赖 + 对未登录词稳健。jieba 遇到新产品名、人名会切错，一旦切错就彻底漏召回；
bigram 最多是切得"碎"，不会切"错"。代价是索引略大、有少量无意义组合。
（如果允许加依赖，jieba 的精度确实更高。）

**Q: 精排分数是绝对的吗？怎么和阈值配合？**
`bge-reranker` 输出 sigmoid 后的 `[0,1]` 分数，通常相关 > 0.5、不相关 < 0.1；
本地精排的每个特征也都被设计成绝对分。所以 `kb.rerank.min-score=0.15` 是有意义的门槛。
若推理服务返回的是原始 logit，代码会检测并做 sigmoid，而不是 min-max 归一化。

**Q: 三层里哪一层收益最大？**
看失败模式占比。一般是**精排**（直接决定模型看到什么，且成本最低，11ms），
其次是**改写**（堵住"检索不到"这类硬失败，但延迟代价最高）。
建议的做法是**做消融**：关掉某一层，看命中率和答案质量的变化——
本工程把 `useRewrite` / `useHyde` / `kb.rerank.mode=off` 都做成了可切换的开关，
就是为了能直接跑这个对比。

**Q: 怎么知道某次问答是召回的问题还是精排的问题？**
看响应里的 `hits[].routes` 和分层分数：

- 期望的段落**根本不在 `hits` 里** → 召回问题（放宽 `min-vector-score` / 调大 `recall.top-k` / 检查分词）；
- 它在 `hits` 里但**排得很靠后**被 `topK` 截掉了 → 精排问题（加候选数 / 换 bge-reranker）；
- 它在前面但模型**答非所问** → 生成问题（改 Prompt / 换模型）。

这个判断链路就是 `Candidate` 刻意保留每一层分数、而不是只留一个最终数字的原因。

## 7. 可以继续做的优化

按"性价比 × 面试含金量"排序：

1. **改写流式化 / 条件触发**：当前改写串行占了一半延迟。
   长问题且无指代时可跳过改写，或用小模型做改写；
2. **向量索引**：把 `vectorRecall()` 的 `O(N)` 全量扫描换成 HNSW/IVF，
   接口已抽象好，改一个方法即可；
3. **语义切分**：现在是"标题 + 字数"切分，可换成按句向量相似度断点切分，
   让每个块内部语义更聚合；
4. **父块检索（Small-to-Big）**：用小块做检索（匹配准），返回时带上它所属的父块（上下文全）；
5. **自动参数调优 / 评测集**：手工造 20~50 条 (问题, 期望片段) 就能算
   Recall@K、MRR，让"加一层有没有用"从感觉变成数字。**这是最容易被忽略、
   但在面试里最能体现工程素养的一步。**
